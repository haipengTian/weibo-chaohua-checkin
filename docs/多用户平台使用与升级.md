# 多用户平台：本地使用与升级

平台入口是 `portal:app`。用户端 `/`，管理端 `/admin`，两端共用服务端会话，只有管理员能访问管理接口。

## 先在本地使用

在仓库根目录创建虚拟环境，并安装依赖：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
$env:PANEL_USER = 'avatar'
$secret = Read-Host '首次管理员密码（12–128 位）' -AsSecureString
$env:PANEL_PASSWORD = [System.Net.NetworkCredential]::new('', $secret).Password
$env:PORTAL_COOKIE_SECURE = '0'
.\.venv\Scripts\python.exe -m uvicorn portal:app --host 127.0.0.1 --port 8788 --workers 1
```

打开 `http://127.0.0.1:8788`。`PORTAL_COOKIE_SECURE=0` 仅用于本机 HTTP；公网 HTTPS 必须使用默认值 `1`。

首次启动创建环境变量指定的管理员，之后使用数据库中的密码；修改环境变量不会重置密码。用户名 3–32 位，允许字母、数字、中文、下划线、点和短横线，大小写不区分。密码 12–128 位。

### 用户的操作

1. 在登录页注册平台账号，登录后点「绑定微博」。
2. 用微博 App 扫码并确认。一个平台用户可以绑定多个微博。
3. 首页「每日自动签到 → 修改计划」打开居中弹窗，选择时间、启用并保存；也可从底部「我的 → 每日计划」修改。计划对本人绑定的全部微博生效，新用户默认暂停。
4. 首页「我的微博」展示每个账号的登录状态、签到范围和今日结果，可手动「签到」。账号卡片上的「检测登录」和「重新扫码」用于维护微博登录；点击卡片上的「签到记录」，进入历史页并按该微博 UID 筛选，不限制日期。
5. 首页顶部的「签到足迹」按微博账号和时间范围展示成功天数，以及不受范围限制的当前连续签到天数。「本月」展示自然月，「近一年」「近两年」分别用热力图展示截至当天的 365 天、730 天；图表超出屏幕时可横向查看。点击日期打开「签到详情」小票弹窗，每次显示一条执行记录。同日有多条记录时，用「上一条」和「下一条」切换。要查看另一微博，关闭弹窗后在足迹中切换账号。
6. 点某个微博的「配置签到」，在居中弹窗中选择签到范围。扫码后自动扫描关注列表；已有账号首次查看会扫描，也可点右上角「刷新」。扫描只读取列表，不执行签到；配置列表只展示选择，签到结果在详情中查看。
7. 选择「全部关注的超话」或「只签到选中的超话」。自选模式支持按名称搜索、逐项勾选和全选；搜索时只修改当前结果。点底部「保存设置」生效并关闭；取消或关闭时若有修改，会提示是否放弃。每个微博独立保存，手动与定时共用范围。全部模式包含以后新关注的超话，自选模式需手动勾选新关注。空选并保存会暂停这个微博。列表未读完整时需先刷新，才可从全部切为自选；已有自选名单编辑时保留未显示的选择。
8. 签到记录及首页日历的详情弹窗展示每个超话的结果，区分此前已签到、本次成功、失败、未执行和未识别状态。未保存逐项明细的旧记录只显示已有汇总。

同一个微博在当前签到范围当天完整成功后，按钮显示「今日已签到」并禁用，后端拒绝重复提交，不再新增签到记录。失败或部分失败仍可手动重试。北京时间次日恢复「签到」；页面保持打开时会自动更新，后台标签页重新进入时也会刷新。更改签到范围后可执行新范围；切回当天已经成功的相同范围仍会拦截重复提交。签到任务排队或执行期间不能修改范围。

用户端底部悬浮导航包含「首页、签到记录、我的」，桌面常驻，鼠标靠近时图标连带放大；手机点击右下角菜单按钮展开。右上角头像也可进入「我的」，这里可修改每日计划、切换深色模式和退出登录；管理员另有管理控制台入口。

管理端继续使用侧栏。点击顶栏左侧按钮可收起或展开，桌面收起后保留导航图标并记住状态；手机上该按钮开关导航抽屉。

日历按北京时间统计。一天只要有一次完整成功就标记「成功」，重试不重复增加成功天数；否则依次显示执行中、部分失败或失败。没有执行的日期显示「无记录」。当月成功天数随月份切换；当前连续签到天数跨月份计算，今天未成功时从昨天向前连续计数。

同一用户重扫同一个 UID 会更新原绑定；其他用户扫码会提示「该微博账号已被绑定」，不改变归属。首版不提供解绑、转移或密码登录微博。

### 管理员的操作

从侧栏进入管理控制台，查看全站用户、微博数量、登录异常、执行记录与事件日志。记录页支持完整平台用户名、微博 UID、结果及日期范围筛选，日期两端都包含在范围内；汇总与下方执行明细使用相同条件。

在「用户列表」点击「添加用户」，填写用户名、初始密码和确认密码，创建普通用户。成功后列表定位到新用户，管理员保持当前登录；将初始密码安全交给对应用户。用户名和密码规则与注册相同。

「系统设置 → 开放用户注册」默认开启。关闭并保存后，登录页不再显示注册入口，直接调用注册接口也会被拒绝；管理员仍可添加用户，已有用户正常登录。重新开启后恢复公开注册。设置持久化，无需重启服务；已打开的登录页刷新后同步入口。

管理端不提供代签、代改计划、禁用用户或导出登录凭据。创建用户和注册开关变更会记录操作管理员及事件，不保存明文密码。

## 调度、状态与统计

- 每个平台用户共用一份计划，对其全部微博生效。按 `Asia/Shanghai` 每 30 秒检查到期任务，可能比所选时间晚几十秒；一次账号任务顺序处理其选定范围内的超话。
- 成功后同一北京时间日期不再自动执行；失败后的下一次自动尝试距上次自动任务**结束**至少 10 分钟，每账号每种签到范围每日最多 3 次自动尝试。手动任务不计入这 3 次上限。
- 停机后只补执行当天已到时间且未完成的账号，不补过去日期。排队任务跨日后中止；长任务跨日停止后续超话操作。重启中断留下独立记录。
- 暂停不再创建自动任务；已经排队或开始的任务继续处理。
- 每 10 分钟检查是否有账号满 6 小时未检测，符合条件时进行登录检测。检测与签到都保存微博返回的新 Cookie；有效期仍由微博决定，失效后需重新扫码。
- 网络/接口异常、登录失效、业务失败、部分失败、无超话分别记录。无超话、未识别按钮和未拉完整列表不会计为成功，也不抑制当日补执行。
- 「执行」以账号任务为单位；「新签超话」是所选记录内新签成功数，之前已签数量单列。指定模式下的总数、已签、新签、失败和逐项明细仅统计选中范围，关注列表仍显示全部超话；已选超话未在扫描结果中找到时记为待确认，不计为完整成功。反复尝试产生多条记录，统计不把执行次数解释成唯一账号数。
- 用户数、绑定数、登录异常是当前快照；日期筛选影响执行记录与超话次数。异常页根据当前登录状态与最近一次执行结果展示，不按历史日期筛选。

## 数据与恢复

`data/portal.sqlite3` 保存用户、角色、会话摘要、微博归属、Cookie、个人计划、执行记录及安全事件。密码使用带随机盐的 scrypt；会话使用 HttpOnly、SameSite=Strict Cookie，默认 Secure，有效期 30 天。用户退出、离线重置密码会撤销对应会话。

微博 Cookie 是服务端敏感数据，数据库没有额外加密；限制目录和备份访问权限，不提交到 Git。新建数据目录在 Linux 下为 `0700`，数据库文件为 `0600`。日志只记录固定摘要，不保留微博换票地址、Cookie、用户密码或原始异常响应。首版保留全部平台执行记录，尚未自动清理日志。

忘记平台密码时，先停止**新平台服务**，在相同数据目录运行：

```powershell
.\.venv\Scripts\python.exe portal_manage.py reset-password --username avatar
```

命令交互读取新密码，撤销该用户全部旧会话。也可以在停止容器后用 `docker compose --env-file .env.portal -f compose.portal.yaml run --rm --no-deps weibo-portal python portal_manage.py reset-password --username avatar`。

## 不需要旧账号和记录时：直接替换旧面板

目标服务器使用旧部署 `/opt/weibo-checkin/compose.yaml` 时，可由 root 执行 `scripts/deploy-fresh.sh`。它从 GHCR 拉取固定 digest 的 `portal-v0.1.1` 镜像，在 `/opt/weibo-portal` 创建全新数据库，沿用原 `127.0.0.1:8787` 和 `wb.thpvip.xyz`；无需调整 Nginx。

不需要克隆源码，在服务器下载并执行脚本即可：

```bash
curl -fSL https://raw.githubusercontent.com/haipengTian/weibo-chaohua-checkin/codex/multi-user-portal/scripts/deploy-fresh.sh -o /root/deploy-weibo-portal.sh
bash /root/deploy-weibo-portal.sh
```

镜像拉取和配置准备期间旧服务继续运行。准备完成后停旧容器、启动新版，检查健康接口、现有域名 HTTPS 及匿名接口 401；成功后移除旧容器。启动或检查失败时尝试恢复旧服务（容器已移除时用原镜像重建），报告恢复结果，并保留新版日志供排查。

新版管理员为 `avatar`，随机密码保存在服务器 `/opt/weibo-portal/.env.portal`，脚本给出本机查看命令。旧用户、微博绑定、计划和记录不导入；登录后重新扫码并设置计划。旧数据文件不接入新版，青龙不参与替换。重跑脚本沿用已创建的新版数据库和密码。

### 已部署多用户平台时，只更新镜像

不再执行旧版替换或重建数据。对已通过上述脚本部署的 `/opt/weibo-portal`，更新至 `portal-v0.1.5`：

```bash
cd /opt/weibo-portal &&
sed -i 's|^PORTAL_IMAGE=.*|PORTAL_IMAGE=ghcr.io/haipengtian/weibo-chaohua-checkin:portal-v0.1.5|' .env.portal &&
docker compose --env-file .env.portal pull &&
docker compose --env-file .env.portal up -d --no-build --wait
```

继续挂载原 `portal-data/`，现有用户、密码、微博绑定和记录保留；启动时自动补齐缺少的签到范围与执行范围表。登录后可在管理端创建用户、关闭公开注册，在用户端查看关注超话和选择签到范围。不要删除数据卷或覆盖数据库。

如需在 QQ 查询签到或接收登录失效提醒，按[麦麦接入说明](../integrations/maibot/README.md)从同一个镜像提取插件并配置只读接口。

## 需要保留旧账号时：迁移后切 Nginx

当前线上旧版位于 `/opt/weibo-checkin`，使用 `127.0.0.1:8787`；新候选默认使用 `127.0.0.1:8788` 和独立的 `portal-data/`。`ql.thpvip.xyz` 及青龙服务不参与迁移。

以下是部署时的操作流程，本轮开发没有执行远端命令。停止旧服务、迁移真实数据、启动新候选和切换 Nginx 均需在部署阶段确认。

1. **固定恢复点**：记录旧镜像 digest、旧 Compose、`.env` 和 Nginx 站点配置。短暂停旧签到服务，对旧 `data/` 作一致备份，然后让旧服务继续运行。不要在复制过程中允许旧程序写 JSON。
2. **隔离候选数据并暂停候选计划**：从备份复制 `accounts.json`、`settings.json` 等旧文件到新仓库的 `portal-data/`；不要把正在使用的旧数据目录直接挂给新服务。确认旧微博全部归指定管理员。**在执行第 4 步迁移前**，仅编辑候选 `portal-data/settings.json`，将 `enable_daily` 设为 `false`，其余设置保留。原始恢复备份和旧服务数据保持原样。这样导入 SQLite 的候选计划才是暂停状态，避免旧、新计划同时对真实微博执行。
3. **准备环境**：在独立的新目录保存本仓库的 `compose.portal.yaml`，复制 `.env.portal.example` 为 `.env.portal`，填写原管理员用户名、强密码和 `PORTAL_IMAGE` 固定版本。首次发布为 `ghcr.io/haipengtian/weibo-chaohua-checkin:portal-v0.1.0`；镜像发布成功且服务器具备拉取权限后再继续。Linux 上用 `install -d -m 700 -o 10001 -g 10001 portal-data` 创建目录；已有候选文件也需归 UID/GID 10001 所有。只调整新候选目录，不改旧目录。
4. **拉取镜像和迁移**：

   ```bash
   docker compose --env-file .env.portal -f compose.portal.yaml pull
   docker compose --env-file .env.portal -f compose.portal.yaml run --rm --no-deps \
     weibo-portal python portal_manage.py migrate-legacy --owner avatar
   ```

   将 `avatar` 换成已核对的原管理员用户名。命令先在候选目录内备份原始 JSON，再事务导入账号及每日计划，保留原账号 ID。重复执行不会重复导入。UID 缺失/重复、ID 重复或数据冲突会使整次导入回滚，原 JSON 保留。

   服务器无需源码和 Node.js。Compose 保留 `build: .` 供本地源码构建使用；服务器启动一律带 `--no-build`。自行构建时，可将上面的 `pull` 换成 `build`，其余迁移步骤相同。

   旧密码、旧全局通知渠道、旧面板会话不导入新平台。原始 JSON 日志留在备份中，不当作多用户平台的新执行记录；旧最近结果仅用于判断今日是否已经完整成功，不生成虚假的历史统计。
5. **确认候选自动计划已暂停**：迁移会读取第 2 步候选副本中的暂停状态。迁移后再修改 JSON 不影响 SQLite，也不能靠重跑迁移更新计划；若已误导入开启状态，应先停止旧服务，再启动候选并在用户端暂停。验收期间只手动执行已授权的测试账号，正式切换后再开启每日计划。
6. **启动与检查**：

   ```bash
   docker compose --env-file .env.portal -f compose.portal.yaml up -d --no-build --wait
   curl -fsS http://127.0.0.1:8788/healthz
   ```

   经 HTTPS 临时入口或验证环境检查管理员、旧微博归属、两个新用户的数据隔离、真实扫码、真实签到和计划执行。候选默认 Secure Cookie，直接用公网 HTTP 不会保持登录。
7. **核对反代**：Nginx 保留 `Host`，设置 `X-Forwarded-Proto $scheme` 与 `X-Forwarded-For $proxy_add_x_forwarded_for`。在 `.env.portal` 的 `FORWARDED_ALLOW_IPS` 中填写 Nginx 连接到容器时的实际来源 IP（通常是该 Compose 网络网关），重建候选后验证登录。不要直接填 `*` 或相信公网任意转发头。转发错误会导致来源校验失败，或不同用户共享限流额度。
8. **批准切换后**：停止旧签到服务，再把 `wb.thpvip.xyz` 的现有 Nginx upstream 从 `8787` 改为 `8788`；先 `nginx -t`，通过后 reload。验证 HTTPS、匿名 401、管理权限、扫码与当日任务，随后按实际需要在新用户端开启每日计划。旧容器、数据和镜像保留用于恢复。

### 回退

停止新平台，恢复之前保存的 Nginx upstream 和旧服务，执行 Nginx 配置检查并 reload。旧 JSON 一直未被新程序修改，可继续使用；切换后在新平台新增的用户、绑定和计划只在 SQLite 中，不能倒灌给旧版，应保留新库备份。

同一候选数据目录只允许一个平台进程，生产使用 `--workers 1`，不要启用热重载或扩容副本。启动与离线管理使用同一进程锁，避免重复调度或在线重置。

## 本地验证

表单控件使用 `frontend/src/components/ui/` 中按需复用的 credit-ui React 组件，Vite 构建为同源静态文件，不需要 Next.js 或 Node 运行服务。登录、搜索、结果筛选、日历、计划时间与开关统一使用这些组件。时间弹层分别选择小时、分钟，点「确定时间」后再保存计划；「取消」不会改变原时间。日期以北京时间日期条件提交，支持清除单端日期和重置筛选。

仓库中的 `static/portal/components/` 可直接供 Python 服务使用；改动前端源码后，在 Node.js 22 环境重新构建，并保留更新后的产物：

```powershell
cd frontend
npm ci
npm run build
cd ..
```

Docker 会自动执行同样的前端构建；镜像运行时无需 Node。页面为 Radix 动态样式提供每次响应独立的 nonce，反代不要另外覆盖为不含该 nonce 的 CSP。

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest -q
```

浏览器隔离测试服务：`python -m tests.preview_server`，仅监听本机 8788，数据在 `.preview/browser/`，所有扫码和微博请求使用测试替身、关闭调度。该服务用于界面验收，不能替代真实扫码/签到验收。详细证据见 `docs/多用户平台验收记录.md`。

前端回归使用同一隔离服务。先确保 8788 未被正式本地平台占用，再运行以下命令；Playwright 自动启动测试服务。已有该隔离服务时，本地会复用它：

```powershell
$env:PREVIEW_PYTHON = (Resolve-Path .venv/Scripts/python.exe).Path
cd frontend
npx playwright install chromium
npm run test:e2e
```

也可设置 `$env:PLAYWRIGHT_CHANNEL = 'chrome'` 使用本机 Chrome。用例覆盖时间确认/取消/保存恢复、失败反馈、键盘选择、日期查询参数、用户搜索、注册以及 390px 深色弹层布局；浏览器设为洛杉矶时区，检查日期不会偏移。CI 安装 Chromium 并运行同一组用例。
